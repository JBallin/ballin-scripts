# Verification collector qualification

`backup verify` compares ordinary file sources and filtered preferences directly. It also supports the following narrowly qualified command paths on macOS:

- npm 11.19.0's unmodified registry artifact or the npm artifact bundled in the official Node 24.21.0 macOS arm64 release, including bundled dependencies, on Node 24.21.0. The verifier resolves the normal npm CLI layout, checks the artifact fingerprint without executing it, and invokes that CLI directly through the current Node executable. It preserves HOME, prefix, config and cache; supported flags disable update notifications and timing. Shell wrappers, modified artifacts, other runtimes and code-loading controls remain unchecked.
- Homebrew prefix discovery for the fingerprinted shell fast path from source revision `8e858db5584704dcd469b8e826228c0d5a5a94f6`. Prefix and repository must use the ordinary colocated layout. Custom brew.env files and alternate layouts remain unchecked. The direct privileged-mode Bash invocation preserves HOME and uses the system utility PATH that Homebrew normally selects. The resulting bash completion directory is listed through `/bin/ls`; it uses the same stdout and normal snapshot normalization as the writer.

Qualification used independently disposable installations with dummy state. Both npm distributions' healthy, stale-lock and malformed-package fixtures each exited zero twice with identical inventory stdout; package/config/runtime file hashes and modes were unchanged. Instrumented network and subprocess attempts were absent. Writes were ordinary npm cache/log creation. Negative controls demonstrated that the tested guard paths reject network, child processes and writes outside the fixture. These guards are supporting evidence, not complete OS-level native isolation.

Homebrew prefix, formula and cask listings ran against empty, populated and broken-cask-link fixtures, twice each. Source/package/HOME files were unchanged and repeat stdout matched. A malformed npm package still prints `dummy@` with success, and a broken cask symlink still appears in the list with success and a warning. Verification checks normalized inventory correspondence, not package health; raw tool stderr is never printed.

Basic Homebrew lists are not enabled yet: their shell fast path can fall through to Ruby when expected directories disappear. Ruby setup can install or upgrade portable Ruby. `leaves`, `services` and `bundle dump` also involve Ruby/formula/tap or nested collector startup, so prefix evidence cannot qualify them. The verifier reports them unchecked rather than risk bootstrap, repair or services changes.

Remaining qualification requires independent dummy environments: Homebrew Ruby/tap/nested Brewfile cases, pipx legacy/damaged venv maintenance, uv/pyenv tool roots, editor profiles/extensions, and a disposable macOS service/App Store namespace. The current host's services, App Store account and editor profiles were not accessed. Nested `sandbox-exec` is unavailable in the execution sandbox; testing real host service/account paths would require a separately supported disposable environment. Absent tools remain expected skips; selected available unqualified collectors make verification incomplete.

A later tool artifact can be supported after proportionate disposable qualification and an updated gate. No npm log-rotation/cache-sentinel mechanism is a permanent product contract; harmless bookkeeping remains allowed. HOME, prefixes and profiles are never substituted during production verification to make a collector appear safe.

Static qualification findings behind the remaining limits:

- The pinned Homebrew source's `utils/ruby.sh` calls `brew vendor-install ruby` when the portable runtime is missing or the `current` runtime differs from the expected version. `HOMEBREW_NO_AUTO_UPDATE` does not remove this bootstrap path. A disappearing Caskroom can cause `list.sh` to return failure and enter Ruby startup.
- Homebrew services' `CLI.running` calls `launchctl list`; its service lookup also uses the UID-scoped launchd domain. A dummy HOME is not a separate service namespace. Nested Brewfile output uses extension collectors, including npm and App Store/editor inventory paths, so prefix/basic-list evidence does not qualify the complete dump.
- Public pipx 1.9.0 source performs `rmdir(paths.ctx.trash, False)` in generic CLI setup; its `rmdir` calls `shutil.rmtree`. The same version marks `--skip-maintenance` deprecated/no-op. Suppressing shared-lib upgrades cannot by itself establish that managed state will be preserved. No pipx installation was executed to test this finding.
- The installed VS Code public wrapper (version 1.140.0) starts its Electron executable with `ELECTRON_RUN_AS_NODE=1` and forwards Node options through VS Code-specific variables. No editor profile or extension data was read and the CLI was not launched. Meaningful native startup qualification needs a disposable app/profile environment with an enforceable boundary around host credentials/services; the current nested sandbox cannot provide that boundary.

uv and pyenv were absent from the execution PATH. Additional public-artifact/dummy-tool-root qualification ran without account or backup operations: uv 0.12.22 invokes each tool environment Python during listing; a dummy interpreter changed managed fixture state while uv exited zero. Its source explicitly uses `-I -B` without `-S`, so site initialization remains active. pyenv 2.6.8 empty/populated fixtures preserved state, but a plugin-provided `sort` changed managed fixture state while output remained identical and exit zero. Generic uv/pyenv invocation is therefore not enabled. A future narrowly supported pyenv path could bind core/native-extension and resolved utility artifacts and refuse plugin overrides without changing the observed root; that is feasible implementation work, not an authorization blocker. App Store and host services require the separate native namespace described above. Unsafe or unqualified available paths remain explicit incomplete outcomes, never omitted from the selected-source denominator.

Writer parity also requires the same resolved Bash, npm and Node executables. Nonempty shell startup/options or exported functions make npm unchecked; the verifier never reads or executes startup files. Completion listing requires PATH resolution to the qualified `/bin/ls`, preserving the writer cwd. Empty PATH entries participate in this check. Private collector directories are removed even if output-file creation fails.
